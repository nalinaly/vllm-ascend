CSA 算子参数对齐需求

给 pypto-lib 的需求说明 · 基于 aclgraph FULL_DECODE_ONLY 下 8 个 decode 步的实测 · bs=4 · 3 层 DeepSeek-V4 · TP=1 · 单 A3 die

我们已经把 PyPTO 的 CSA 算子接进 vLLM 的 decode 路径并在图模式下跑通。 接下来能靠自己把主要开销（20.8 ms/步）压掉， 但会剩下 约 1.0–1.5 ms/步 的索引转换消不掉。 这部分开销的存在，唯一原因是算子的入参约定与 vLLM 实际的数据布局对不上。 它在转换层里无解，需要 lib 侧提供一个入参对齐的版本。

一、背景

这件事在做什么：把 DeepSeek-V4 模型里一层的注意力计算， 从昇腾厂商提供的算子换成 PyPTO 写的 CSA 算子，并且是在 vLLM 的真实推理服务里换， 不是在算子测试台上跑。目的是验证 PyPTO 算子能不能在生产推理路径上顶替厂商实现。

两边的数据组织方式不一样，所以中间必须有一层翻译。 算子是在 pypto-lib 的测试台上开发的，入参由测试台按算子自己的约定构造； 真实服务里这些数据全部由 vLLM 的显存分配器管理，按 vLLM 自己的约定存放。 这层翻译就是下图中间那块，每个 decode 步都要做一遍。

转换层的两段合计 22,881 us/步，是算子本体的 23 倍。数据来源见页脚。

名词含义
页 / block KV cache 不是连续一整块，而是切成固定大小的页按需分配。 vLLM 的页是 128 行，算子要的页是 32 行
块表 / block table 每个请求一行，记录它的第 j 个逻辑页放在哪个物理页。 两边的块表按各自的页大小编号，数值对不上
槽号 / slot mapping 本步要写的那一行在 cache 里的位置。同样是两套编号
六份 cache 这一层的注意力需要六份状态：滑窗 KV、压缩 KV、主压缩器 state、 indexer 压缩器 state、indexer key、indexer scale。 算子对六份都是读写（pl.InOut），不只是读
图模式 / aclgraph 把一串算子调用录成一张图反复重放，省掉每步的 host 侧开销。 重放时 Python 不执行，所以翻译逻辑必须能被录进图里， 不能是「先在 host 上算好再塞进去」

进展：46 个参数能在真实 decode 状态上组装、注册、下发、执行； eager 下连续 190 步无故障；图模式下捕获通过，且确认算子确实在重放的图里执行 （profile 里每个 decode 步都有 simpler_aicpu_kernel_exec，原生那轮为 0）。 功能层面是通的，剩下的是代价问题。

三、搬运：这部分我们自己能修

vLLM 用 as_strided 在一块 padded 缓冲上切出多份逻辑 cache， 所以它们都是非连续视图；而 PyPTO 的绑定层明确拒收非连续张量。转换层现在的做法会让 torch_npu 先把整块缓冲变连续再取数——代价与取几页无关，取 64 页和取 34730 页一样贵。

四、索引：修完搬运之后剩下的，我们修不掉

五、错配在哪里

逐条列出算子入参约定与 vLLM 实际布局的差异，以及各自逼出了什么代价。

错配具体差异逼出的代价权重
压缩器 state 的组织方式算子要每请求 16 行的私有环，自带块表；vLLM 按自己的分配器分页存整套建环/回写代码，含 AI_CPU 上的 scatter最大

页大小那一条说明这类问题是可以被消除的：算子页 32 行、vLLM 页 128 行， 正好 4 倍，块表列号换算一下就完事，零开销。其余几条之所以贵，是因为差异不是整数倍关系， 或者根本是两种不同的组织方式。

六、需求

请 lib 侧提供一个入参与 vLLM 实际布局对齐的 CSA 算子版本。具体是：

  1. 压缩器 state 直接按 vLLM 的分页取。算子现在要每请求 16 行的私有环， 我们得每步现建一个再写回去。改成接受 vLLM 的块表与页大小，这套代码整体消失。
  2. indexer key 接受带 padding 的页。vLLM 把 key 和 scale 放进同一个 16640 字节页，算子只要前 128 行。若签名能接受 130 行的页并只用前 128 行， 我们就能直接把原缓冲递过去。
  3. indexer scale 改收 FP16。vLLM 按 FP16 存，算子签名要 FP32， 每步一次类型转换。类型转换不可能是一个视图，只有改签名能归零。
  4. 槽号按 vLLM 的口径。让算子按 vLLM 的槽号语义寻址， 省掉每步的槽号映射与窗口索引重算。

四条做完，图内索引运算可以降到接近零。预计每步从 7.2 ms 降到 约 5.6 ms（保守口径）， 对原生的 4.7 ms 约 1.17 倍， 剩下的差距就只是算子本身的计算时间了。

七、为什么不是「改一下现有算子」就够

我们已经在自己的树里剥离并改造过这个算子，所以知道改动面在哪里。 改本身不大：pypto-lib 是纯源码仓，没有构建产物，签名不匹配会在调用时直接报错， 不会静默算错；上游 decode_csa_tp1 的调用点约十来处、分布在五个文件。

真正需要 lib 侧出人的原因是另外三点。

  1. 要改的是算子内部的取数逻辑，不只是签名。让算子按 vLLM 的分页取压缩器 state，意味着它内部的环形寻址要重写，这需要熟悉该算子数值语义的人来做。 我们改得动参数，改不动语义。
  2. 动态轴没有任何校验。用 bind_dynamic 声明的轴编译成 -1， 不与任何东西比对；同一个符号绑在多个参数上时，只以第一个声明它的为准， 其余假定一致。我们注册的入口有 24 处这样的绑定。改错不报错，只算错， 需要作者侧的用例来兜底。
  3. 我们的副本会被覆盖。我们拆出的入口在 pypto-lib 里不存在， 是本地 fork；同步脚本会无条件覆盖闭包内的每个模块。长期维护两份是不现实的， 对齐版本应该在 lib 仓里。

数据来源

msprof 导出的 kernel_details.csv，原生与替换各一轮， 除是否替换外参数完全一致。全部数字由 csa-attn-perf.py 从 trace 重算、 写入 csa-attn-perf.json，本页由 csa-lib-ask-render.py 从该 JSON 生成。 耗时分解的完整版见同目录 csa-attn-perf.html。

口径

8 个 decode 步（warmup 之后），bs=4, prompt 1024, 3-layer DeepSeek-V4, TP=1, one A3 die， FULL_DECODE_ONLY, cudagraph_capture_sizes=[1,2,4]。 算子耗时取 AICPU 派发段与 AICore 执行段的并集：后者在全部 8 步里都嵌套于前者， 相加会把 976 us 说成 1924 us。

哪些是估计值

带 估 与 * 的是预估，其余为实测。 搬运部分的收益是「删掉 trace 里这些行、换成同一 trace 里另一些行」算出来的； 索引部分的三段拆分中，第一段有单点可核对（AI_CPU 的 scatter 每步两次、各 135 us， 删掉一次），后两段是按 op 类型与启动次数推的，误差可能达到数百微秒。 真实收益要重新 profile，判据是 Slice 从 152 次降到接近零。

还未验证

算子本体 976 us 与原生 attention 段约 454 us 的比值（约 2.1 倍）， 是在设备每步搬约 26 GB 的条件下测的，同一轮里两边都有的模型算子也慢了一成。 搬运问题修掉之前，这个比值不能当作算子的真实水平，需要重测。 原生 attention 段的数值来自按层切分的归因，比直接读 CSV 要弱。
